# work-log 페이지: knowledge-graph-db 작업 이력 기록과 조회

## 배경과 목적
- 지금까지 legacy MariaDB(mathdb)에서 knowledge-graph-db(Postgres `kg` 스키마)로 옮긴 작업과, 색인·딕셔너리·플래시카드·퀴즈를 등록하고 삭제한 작업은 한곳에 모인 이력이 없다.
- 단원 수동 결정은 `l2o.unit_override`, 중복 묶음 변경은 `l2o.dedupe_history`, PDF 전환은 `kg.document_convert_log`에 흩어져 있다. 딕셔너리, 플래시카드, 퀴즈, 색인의 등록과 삭제는 어디에도 남지 않는다.
- 그래서 Postgres에 공용 작업 이력 테이블 `kg.work_log`를 만든다. 각 쓰기 경로가 이 테이블에 로그를 남기고, 새 페이지 `/work-log`에서 최근 것부터 날짜별로 본다.
- 서비스가 다시 만들어졌을 때(서버 프로세스 시작) 이력이 하나도 없으면, legacy MariaDB의 `math_concepts`, `questions_units`와 현재 KG에 등록된 내용을 비교한 현황을 기준선 로그 1건으로 남긴다.

## 범위
### 하는 것
- `kg.work_log` 테이블 DDL을 **schema.sql**(`web/db/schema.sql`)에 추가한다. 서버가 시작할 때도 같은 DDL을 실행해, `npm run db:setup`을 돌리지 않아도 테이블이 생기게 한다.
- 서버 전용 모듈 **workLog**(`web/src/lib/server/workLog.ts`, 새 파일)를 만든다. 내용은 기록 함수, 조회 함수, 기준선 시드 함수다.
- 기존 쓰기 경로 4곳에 로그 기록을 붙인다.
  1. 개념 전이: **l2oKg**(`web/src/lib/server/l2oKg.ts`) `writeGroupToKg`
  2. 딕셔너리, 플래시카드, 퀴즈, 색인 일괄 등록: `web/src/app/api/dictionary/route.ts` POST, `web/src/app/api/dictionary/process/route.ts`
  3. 색인 zip 업로드: `web/src/app/api/book-indices/route.ts`(**dictionaryDb** `saveBookIndexChapters`)
  4. 항목 삭제: `web/src/app/api/dictionary/route.ts` DELETE
- 조회 API `GET /api/work-log`를 만든다.
- 조회 페이지 **WorkLogPage**(`web/src/app/work-log/page.tsx`, 새 파일)를 만들고, **AppHeader**(`web/src/components/AppHeader.tsx`) NAV에 "작업 이력" 링크를 추가한다.
- 서버 시작 훅 `web/src/instrumentation.ts`(Next.js `register()`, 새 파일)를 만든다. 이 훅이 테이블을 보장하고 기준선 시드를 실행한다.
- **docs/COMPONENTS.md**에 WorkLogPage, workLog, instrumentation 항목을 추가한다.

### 하지 않는 것
- 기출문제를 KG로 옮기는 기능은 만들지 않는다. 이 기능은 카드 #196 exam_problems2concepts의 범위다. 이 카드에서는 category `problem`과 기록 함수만 준비하고, 문제 관련 실제 수치는 기준선 로그에만 담는다.
- 과거 작업의 이력을 소급해서 행 단위로 다시 만들지 않는다. 과거는 기준선 로그 1건으로 대신한다.
- 로그를 수정하거나 삭제하는 UI와 API는 만들지 않는다.
- legacy MariaDB에 쓰지 않는다. **legacyDb**는 계속 READ ONLY 세션으로 SELECT만 한다.
- 기존 `l2o.*` 이력 테이블과 **HistoryDialog**는 바꾸지 않는다.
- 도서 TOC, 그래프 편집 같은 다른 KG 쓰기(**graphDb**)에는 로그를 붙이지 않는다.

## 변경할 동작

### 1. 테이블 (schema.sql 끝에 추가, 여러 번 실행해도 안전)
```sql
CREATE TABLE IF NOT EXISTS kg.work_log (
  id         BIGSERIAL PRIMARY KEY,
  category   TEXT NOT NULL CHECK (category IN ('concept','problem','book_index','dictionary','flashcard','quiz','descriptive_quiz','baseline')),
  action     TEXT NOT NULL CHECK (action IN ('create','update','delete','migrate','baseline')),
  summary    TEXT NOT NULL,             -- 화면에 보이는 한 줄 설명
  item_count INT  NOT NULL DEFAULT 1,   -- 이 로그가 다룬 항목 수
  book_stem  TEXT,                      -- 도서 관련 작업이면 도서 stem
  detail     JSONB NOT NULL DEFAULT '{}'::jsonb,
  actor      TEXT,                      -- 로그인 사용자 id, 시스템 작업이면 'system'
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_work_log_created ON kg.work_log (created_at DESC, id DESC);
```
- category의 뜻
  - `concept`: MariaDB 개념을 KG 개념으로 옮김
  - `problem`: 문제(#196에서 사용)
  - `book_index`: 색인
  - `dictionary`: 딕셔너리
  - `flashcard`: 플래시카드
  - `quiz`: 객관식 퀴즈
  - `descriptive_quiz`: 서술형 퀴즈
  - `baseline`: 기준선
- 퀴즈 항목에 `quiz_type === 'descriptive'`가 있거나, options가 없거나 빈 배열이면 서술형(`descriptive_quiz`)으로 분류한다. 나머지는 `quiz`다.

### 2. workLog 모듈 (`web/src/lib/server/workLog.ts`)
- `ensureWorkLogTable(client?)`는 위 DDL을 실행한다.
- `writeWorkLog(entry, client?)`는 1행을 INSERT한다.
  - `client`(PoolClient)를 넘기면 그 트랜잭션 안에서 기록한다.
  - `client`가 없으면 **l2oPool**의 `pool`로 기록한다. 이때 실패하면 `console.error`만 하고 예외를 던지지 않는다. 로그 실패 때문에 본 작업 응답이 실패하면 안 된다.
- `writeWorkLogs(entries[], client?)`는 여러 건을 한 번에 기록한다. 0건이면 아무것도 하지 않는다.
- `listWorkLogByDate(date?: string)`는 아래 API 응답 객체를 돌려준다.
- `seedBaselineIfEmpty()`는 아래 4절의 기준선 시드다.
- 날짜의 기준은 `Asia/Seoul`이다. 하루는 `(created_at AT TIME ZONE 'Asia/Seoul')::date`로 정한다.

### 3. 쓰기 경로별 기록
- **개념 전이** (`writeGroupToKg`): COMMIT 직전에 같은 트랜잭션 client로 1행을 기록한다.
  - category는 `concept`, action은 `migrate`, item_count는 1, actor는 `w.judgedBy`가 `override:<id>`면 그 `<id>`이고 아니면 `system`이다.
  - summary 예: `개념 #<rep> → KG 개념 #<conceptId> (단원 <unitId>, 엣지 added|kept|replaced)`
  - detail: `{groupId, legacyIds: members, representativeLegacyId: rep, conceptId, created, unitId, edge, retiredEdges, judgedBy, jobId}`
  - 트랜잭션이 롤백되면 로그도 남지 않는다.
- **POST /api/dictionary**와 **/api/dictionary/process**: 저장에 성공한 뒤 category마다 1행을 기록한다. 0건인 category는 기록하지 않는다.
  - action은 `create`, item_count는 저장된 개수, book_stem은 항목들의 book_stem이다. 여럿이면 첫 값을 쓰고 detail.bookStems에 전부 넣는다.
  - actor는 `session.user.id`다.
  - summary 예: `딕셔너리 12건 등록 (<book_stem>)`
  - quizzes는 `quiz`와 `descriptive_quiz`로 나누어 센다.
- **색인 zip 업로드** (`/api/book-indices`): `saveBookIndexChapters`가 성공하면 `book_index`, `dictionary`, `flashcard`, `quiz`, `descriptive_quiz` 순으로 0건이 아닌 것만 기록한다.
  - action은 `create`, detail은 `{chapters:[n...], unlinked}`다.
  - 퀴즈를 객관식과 서술형으로 나눈 개수는 `saveBookIndexChapters`의 counts에 `descriptiveQuizzes`를 추가해서 얻는다. 기존 `quizzes` 값은 지금처럼 퀴즈 전체 개수로 둔다.
  - 플래시카드와 퀴즈는 단원 단위로 교체된다. 교체로 지워진 개수는 detail.replaced에 넣는다. 별도 delete 로그는 만들지 않는다.
- **DELETE /api/dictionary**: `success === true`일 때만 1행을 기록한다.
  - category는 type에 따라 정한다. `dictionary`→`dictionary`, `flashcards`→`flashcard`, `index`·`bookIndex`→`book_index`, `quizzes`→삭제 전에 조회한 행이 서술형이면 `descriptive_quiz`, 아니면 `quiz`.
  - action은 `delete`, item_count는 1, actor는 `session.user.id`다.
  - summary 예: `플래시카드 삭제: <front 앞 40자>`
  - detail: `{id, bookStem, term|front|question}`

### 4. 기준선 시드 (서비스 시작 시)
- `web/src/instrumentation.ts`의 `register()`는 `process.env.NEXT_RUNTIME === 'nodejs'`일 때만 workLog를 동적 import한다. 그 뒤 `ensureWorkLogTable()`과 `seedBaselineIfEmpty()`를 실행한다.
- 실행이 끝나기를 기다리지 않는다. 실패하면 `console.error`만 하고 서버 시작은 막지 않는다.
- `seedBaselineIfEmpty()`의 순서
  1. 트랜잭션 안에서 `pg_advisory_xact_lock`으로 동시 실행을 막는다.
  2. `SELECT 1 FROM kg.work_log LIMIT 1`에 행이 있으면 아무것도 하지 않는다.
  3. 비어 있으면 아래 수치를 모아 1행을 기록한다.
- Legacy 수치는 **legacyDb**에 SELECT 전용 함수를 추가해서 얻는다.
  - `math_concepts`: 전체 수, `is_on=1` 수
  - `questions_units`: 전체 행 수
  - MariaDB에 접속하지 못하거나 `MARIADB_DSN`이 없거나 테이블이 없으면 해당 값을 null로 두고, 오류 메시지를 detail.legacy.error에 넣는다.
- KG 수치
  - `kg.math_concepts`: `source_id > 0`인 수와 그 개념들이 대표하는 legacy id 수(`source_id` 1개 + `merged_source_ids` 길이의 합)
  - `kg.concept_unit_edges`: 활성(`is_active`) 수
  - `l2o.migration_result`: `status='migrated'` 수. 테이블이 없으면 null이다.
  - 문제 연동 수: KG에 문제 테이블이 아직 없으므로 null이다.
  - `kg.book_index`, `kg.dictionary`, `kg.flashcards`: 수
  - `kg.quizzes`: 객관식 수와 서술형 수(options가 빈 배열이면 서술형)
- 비교값
  - 미이전 개념 수 = legacy `is_on=1` 수 − KG가 대표하는 legacy id 수(0 미만이면 0)
  - 문제 미연동 수 = legacy `questions_units` 행 수 − KG 문제 연동 수. KG 수가 null이면 0으로 계산한다.
- 기록할 행
  - category와 action은 모두 `baseline`, actor는 `system`, item_count는 1이다.
  - summary 예: `기준선: legacy 개념 660(활성 640) / KG 개념 312(legacy 600건 대표) / 미이전 40, questions_units 1234 / 문제 연동 0, 색인 500·딕셔너리 480·플래시카드 300·객관식 200·서술형 50`
  - detail: `{legacy:{mathConcepts:{total, active}, questionsUnits:{total}, error?}, kg:{mathConcepts, representedLegacyIds, activeUnitEdges, migratedGroups, problemLinks, bookIndex, dictionary, flashcards, quizzes, descriptiveQuizzes}, diff:{conceptsNotMigrated, problemsNotLinked}}`
- 이력이 이미 1건이라도 있으면 다시 시작해도 기준선은 추가되지 않는다.

### 5. 조회 페이지 `/work-log` (WorkLogPage)
- 다른 페이지처럼 **AppHeader**를 쓴다. subtitle은 "작업 이력"이고, NAV의 "유틸리티" 뒤에 `{ href: "/work-log", label: "작업 이력" }`을 추가한다.
- 상단 페이지네이션 영역에 아래 순서로 놓는다.
  1. 전체 이력 수: `전체 N건` (`total`)
  2. 현재 날짜와 위치: `YYYY-MM-DD (p / P일)`. p는 최근 날짜를 1로 센 순번, P는 로그가 있는 날짜 수다.
  3. 버튼 `맨앞으로`(⏮): 가장 최근 날짜로 간다.
  4. 버튼 `>`: 바로 이전(더 오래된) 날짜로 간다.
  5. 버튼 `<`: 바로 다음(더 최근) 날짜로 간다.
  6. 버튼 `맨뒤로`(⏭): 가장 오래된 날짜로 간다.
  7. 날짜 입력 `<input type="date">`
  8. eye 아이콘 버튼(lucide-react `Eye`): 입력한 날짜를 조회한다.
- 현재 날짜가 가장 최근이면 `맨앞으로`와 `<`를 비활성화한다. 가장 오래된 날짜면 `>`와 `맨뒤로`를 비활성화한다.
- 한 페이지는 한 날짜(Asia/Seoul 기준 하루)의 로그 전체다. 최근 것부터(`created_at DESC, id DESC`) 목록으로 보여준다.
- 각 행에 보여줄 것: 시각(`HH:mm:ss`), 분류 라벨, 동작 라벨, summary, item_count, book_stem(있을 때), actor
  - 분류 라벨: concept=개념 전이, problem=문제, book_index=색인, dictionary=딕셔너리, flashcard=플래시카드, quiz=객관식 퀴즈, descriptive_quiz=서술형 퀴즈, baseline=기준선
  - 동작 라벨: create=등록, update=수정, delete=삭제, migrate=전이, baseline=기준선
- 처음 열면 날짜 없이 API를 호출해 가장 최근 날짜를 보여준다.
- 입력한 날짜에 로그가 없으면 "YYYY-MM-DD 에는 이력이 없습니다"를 표시하고 목록은 비운다. 이 상태에서 `>`는 그 날짜보다 오래된 가장 가까운 날짜로, `<`는 더 최근의 가장 가까운 날짜로 간다.
- 이력이 0건이면 "기록된 작업 이력이 없습니다"를 표시하고 모든 이동 버튼을 비활성화한다.

## API 계약
다른 프로젝트와 주고받는 것은 없다. 아래는 같은 프로젝트 안에서 화면과 서버 사이의 계약이다.

`GET /api/work-log?date=YYYY-MM-DD`
- 세션이 필요하다(`requireSession`). 세션이 없으면 401이다.
- `date`는 생략할 수 있다. 생략하면 로그가 있는 가장 최근 날짜를 쓴다. 형식이 틀리면 400 `{ error }`다.
- 200 응답:
```json
{
  "total": 1234,
  "dayCount": 37,
  "date": "2026-11-28",
  "pageIndex": 1,
  "firstDate": "2026-11-28",
  "lastDate": "2026-09-01",
  "newerDate": null,
  "olderDate": "2026-11-27",
  "items": [
    { "id": 99, "category": "dictionary", "action": "create", "summary": "딕셔너리 12건 등록 (book-a)", "itemCount": 12, "bookStem": "book-a", "actor": "u123", "detail": {}, "createdAt": "2026-11-28T05:12:33.000Z" }
  ]
}
```
- 필드 정의
  - `total`: 전체 로그 수
  - `dayCount`: 로그가 있는 날짜 수
  - `date`: 조회한 날짜. 이력이 0건이면 null이다.
  - `pageIndex`: 이 날짜가 최근부터 몇 번째인지(1부터). 그날 로그가 없으면 null이다.
  - `firstDate`, `lastDate`: 가장 최근 날짜와 가장 오래된 날짜. 이력이 0건이면 null이다.
  - `newerDate`, `olderDate`: `date`보다 더 최근인 가장 가까운 로그 날짜와 더 오래된 가장 가까운 로그 날짜. 없으면 null이다.
  - `items`: 그 날짜의 로그 전체. `created_at DESC, id DESC` 순서다.
- 날짜는 모두 Asia/Seoul 기준 `YYYY-MM-DD`다.

## 수용 기준
1. `npm run db:setup`을 두 번 연속 실행해도 오류가 없고, `kg.work_log` 테이블과 `idx_work_log_created` 인덱스가 있다.
2. `kg.work_log`가 없는 DB로 서버를 시작하면 테이블이 만들어진다.
3. `kg.work_log`가 비어 있는 상태로 서버를 시작하면, `category='baseline'`인 행이 정확히 1건 생긴다. 그 detail에는 `legacy.mathConcepts.total`, `legacy.questionsUnits.total`, `kg.mathConcepts`, `kg.dictionary`, `kg.flashcards`, `kg.quizzes`, `kg.descriptiveQuizzes`, `kg.bookIndex`, `diff.conceptsNotMigrated` 키가 있다.
4. 서버를 다시 시작하거나 두 프로세스가 동시에 시작해도 baseline 행은 1건을 넘지 않는다. 이력이 1건 이상 있으면 baseline은 추가되지 않는다.
5. `MARIADB_DSN`이 없거나 MariaDB에 접속하지 못해도 서버는 정상 시작한다. baseline의 legacy 수치는 null이고 `detail.legacy.error`에 메시지가 있다.
6. 개념 하나를 KG로 옮기면(migrate-one 또는 override) `category='concept'`, `action='migrate'` 행이 1건 생긴다. detail에 groupId, conceptId, unitId, edge가 있다.
7. `writeGroupToKg`가 실패해 롤백되면 concept 로그도 남지 않는다.
8. POST `/api/dictionary`로 딕셔너리 2건, 플래시카드 3건, 객관식 퀴즈 1건, 서술형 퀴즈 1건(options 빈 배열)을 저장하면 4건이 생긴다. dictionary는 item_count 2, flashcard는 3, quiz는 1, descriptive_quiz는 1이다. 색인 행은 생기지 않는다.
9. 색인 zip을 업로드해 성공하면 0건이 아닌 category마다 `action='create'` 행이 생기고, book_stem은 zip 파일명 stem이다.
10. DELETE `/api/dictionary`로 항목 삭제에 성공하면 해당 category의 `action='delete'` 행이 1건 생긴다. 삭제할 대상이 없어 `success:false`면 로그가 생기지 않는다.
11. 로그 INSERT가 실패해도(예: 테이블 권한 오류) POST와 DELETE `/api/dictionary`, `/api/book-indices`의 응답 상태와 본문은 바뀌지 않는다.
12. 세션 없이 GET `/api/work-log`를 호출하면 401이다. `date=2026-13-01`처럼 형식이 틀린 값은 400이다.
13. GET `/api/work-log`를 date 없이 호출하면 `date`가 가장 최근 로그 날짜이고, `pageIndex`가 1이고, `newerDate`가 null이다. `items`는 createdAt 내림차순이다.
14. 서로 다른 3개 날짜에 로그가 있을 때 가운데 날짜로 조회하면 `pageIndex=2`, `newerDate`=최근 날짜, `olderDate`=가장 오래된 날짜, `total`=전체 행 수, `dayCount=3`이다.
15. 로그가 없는 날짜로 조회하면 `items`는 빈 배열이고 `pageIndex`는 null이다. `newerDate`와 `olderDate`는 그 날짜 기준으로 가장 가까운 로그 날짜다.
16. 날짜 경계는 Asia/Seoul 기준이다. KST 2026-11-28 00:30에 생긴 로그는 2026-11-28 페이지에 나온다(UTC로는 11-27).
17. `/work-log` 페이지 상단에 `전체 N건`이 보이고, 그 뒤에 `맨앞으로`, `>`, `<`, `맨뒤로` 버튼, 날짜 입력, eye 아이콘 버튼이 이 순서로 있다.
18. 각 버튼은 다음처럼 동작한다.
    - `맨앞으로`: firstDate로 이동
    - `>`: olderDate로 이동
    - `<`: newerDate로 이동
    - `맨뒤로`: lastDate로 이동
    - eye 버튼: 날짜 입력값으로 조회
    - 이동할 날짜가 null이거나 현재 날짜와 같으면 해당 버튼은 비활성화된다.
19. 목록의 각 행에 시각, 분류 라벨(예: 서술형 퀴즈), 동작 라벨(예: 삭제), summary, 항목 수, actor가 보인다.
20. 헤더 NAV에 "작업 이력" 링크가 있고, 이 링크는 `/work-log`로 간다. `/work-log`에 있으면 링크가 활성 스타일로 보인다.
21. docs/COMPONENTS.md에 WorkLogPage(`web/src/app/work-log/page.tsx`), workLog(`web/src/lib/server/workLog.ts`), instrumentation(`web/src/instrumentation.ts`) 항목이 있다.
22. legacyDb에 추가한 함수는 SELECT만 실행한다.

## 가정
- 테이블 위치는 `kg` 스키마(`kg.work_log`)로 정했다. "knowledge-graph-db의 PostgreSQL"이 같은 `DATABASE_URL` DB를 뜻한다고 보았다.
- "SERVICE가 RECREATE될 때"는 Next.js 서버 프로세스 시작으로 보고, `instrumentation.ts`의 `register()`로 처리한다.
- "날짜별로 페이지"는 한 페이지가 로그가 있는 하루 하나라는 뜻으로 보았다. 날짜는 Asia/Seoul 기준이다.
- 버튼 순서는 요구사항에 적힌 대로 맨앞으로, >, <, 맨뒤로다. 맨앞=가장 최근, `>`=더 오래된 날, `<`=더 최근 날로 해석했다.
- eye 아이콘 버튼은 날짜 입력값으로 조회하는 실행 버튼으로 해석했다.
- "플래시카드 퀴즈"는 플래시카드와 객관식 퀴즈 두 가지로 보았다. 서술형 퀴즈는 별도 category로 나눈다. kg.quizzes에 quiz_type 컬럼이 없으므로 options가 비어 있으면 서술형으로 판정한다.
- 문제를 KG로 옮기는 코드는 아직 없다(#196). 그래서 문제 로그는 category만 준비하고, 기준선에서는 KG 문제 연동 수를 null로 둔다.
- 기준선의 "비교"는 테이블별 건수와 그 차이로 정했다. 행 단위 대조는 하지 않는다.
- 로그 기록 실패가 본 작업을 실패시키지 않게 했다. 개념 전이만 같은 트랜잭션에 기록해서 결과와 로그를 맞춘다.
- 일괄 등록은 category마다 1행으로 모아 기록한다. 삭제와 개념 전이는 건마다 1행이다.
- 로그 actor는 세션 `user.id`다. 시스템 작업은 `system`이다.
